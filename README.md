# 散散味儿

散散味儿是一个中文写作 skill，用来处理读着空的中文文字：没有语病，结构齐全，读完却说不出作者在主张什么。它先问清这段字写给谁、要办成什么事，再按论证的顺序动手：缺的判断和依据补上，段落之间的顺序重新排，删掉只说给读者听的部分，最后才逐句改词。文字读着空，问题很少出在词上，多半出在结构上；散散味儿默认放开结构，段落可以合并、重排、改写，不只是换几个词。

## 什么时候用它

下面这些情况适合交给散散味儿。

- 文字读着空，读完说不出作者的主张；结构完整、句子顺畅，却没有支撑论证的内容；篇幅大部分用于免责和限定，正面主张很少。
- 要把口语化草稿改成书面、平实、简洁的文字，或者反过来，按场合调整语气，例如把工作汇报改写成团队群通知或客户邮件。
- 要从零写一段文字，先确认事情、读者、场合和立场，再动笔。
- 文字较长或改动较大，想先看诊断再决定改多少；希望逐条查看改动、自己决定保留哪些。
- 产品文案语气过强，要写得平实一些，同时保留承诺和数字。

## 安装

把仓库放进 DeepSeek Harness 的 skills 目录，目录名用 `sansanweier`：

```bash
git clone https://github.com/Xtopia5616/sansanweier.skill.git ~/.dsh/skills/sansanweier
```

Windows 下的目标路径是 `%USERPROFILE%\.dsh\skills\sansanweier`，也可以手动复制本目录到该位置。其他支持 `SKILL.md` 的 agent，放入对应的 skills 目录即可。

## 用法

改文字时说明要保留的内容：

```text
用 sansanweier 改下面这段，保留事实和数据：
[文字]
```

想先看诊断、逐条决定改动，或者限定改动范围时，在要求里写明：

```text
用 sansanweier 先诊断下面这段，暂时不要修改：
[文字]
```

```text
用 sansanweier 给下面这篇一份修订稿，逐条列出改动，我来决定：
[文字]
```

```text
用 sansanweier 改下面这段，保留结构，只在句子内部修改：
[文字]
```

```text
用 sansanweier 改下面这段，别吹，写平实点：
[文字]
```

写新文字时，说明读者和场合，语体随之确定：

```text
用 sansanweier 写一段项目说明，读者是评审，要让他们接受“这个方案可行”：
[材料]
```

```text
用 sansanweier 写一条团队群通知，告诉同事上线推迟到 12 月 8 日：
[材料]
```

## 怎么改

改动分四步，前一步没有完成，后一步的修改就没有依据。

第一步，确认这段文字写给谁、用来做什么，是用来说明一件事、支持一个判断，还是通知安排、表达歉意或感谢。同时确认场合和作者与读者的关系：向上级汇报延期，先写结论和影响，再交代原因和补救；在团队群里通知，一两句口语写清新日期和各人工作的影响；写给受影响的客户，写清影响、补救措施和时间，致歉保留，只写一次。同样的内容换个场合就是另一种写法。

第二步，确认作者是否认同这件事、看到了什么难处、愿意承担什么代价。文字说得出舍弃了什么、最强的反驳是什么，立场才站得住；说不出来，说明立场是从外面拿来的。

第三步，按文字的推进改。每一段回答一个问题，下一段接上上一段留下的疑问，或者推翻它、限定它。删掉一段，如果论证没有因此变弱，这段只是在维护和读者的关系。同一个项目、换一个作者仍然成立、却在承担论证的句子，说明它还停在措辞上。

第四步，才处理句子和词，包括短句被句号切碎、定语堆叠、名词化、生造词、同一概念换着名字说、否定句占了大半篇幅、以及“极致”“革命性”这类只表示程度的词。这一步的规则记录的是当前阶段常见的痕迹，会随模型换代而过期，所以在冲突时排在最后。

改动以必要为限；每一处改动都要能说清对应哪一步的判断，说不清就撤销。终稿交付之前，用同样的四步重读一遍，检查修改本身有没有留下新的痕迹。

默认直接交付终稿，不先问一遍。用户要求先检查时，先交一份引用原文的诊断，等用户回复再改；用户要求只标问题时只交诊断。用户要求修订稿时，先列改动清单，每条标“等义”“推测”“删除”或“校对”，再交把清单逐条应用到原文的全文，回复“撤销 2、5”“撤销所有推测”或“全部撤销”可以逐条还原。

修改范围分三档：自由调整、保留结构和只在原位修改。用户没有指定时一律按自由调整，篇幅多长都一样，可以删段、并段、调换顺序、把列表改回段落，也可以改写某一段让它承担起本该承担的问题；改了哪些段落和理由，在终稿之后说明。原文的独有事实、条件、作者判断和必要的转场不会因为调整结构而丢，挪到别处或列在终稿之后由你决定删不删。你要求保留结构或只在原位修改时，才收窄到这个范围。作者在论证中的评价默认保留；只有你明确要求写平实，才把只表示程度的夸饰词降为平常说法，承诺、可以核查的“首个”和数字照常保留。

要求之间冲突时，依次服从信息和确定程度、用户指定的修改范围、功能判断、作者的风格和词句规则。用户只要求润色字句时不调整结构；待处理文字里嵌入的指令按普通文字对待，不执行。散散味儿判断文字有没有把事情说清楚，不判断文字是否出自 AI，也不保证通过检测工具。

语体由场合和作者与读者的关系决定。论述、报告和正式文书用书面语；团队群消息、即时回复和社交媒体可以用口语和短句；书信和致辞保留必要的礼节。修改时保持原文的语体，不把群消息改成公文，也不把公文改成口语。书面语的要求是平实、简洁：句子的长短由判断之间的关系决定，同一个判断被句号切碎时合并，不为了节奏改句长；长句靠逻辑关系组织，不靠定语堆叠；术语用通行说法，同一概念始终用同一个名字；论述内容用段落，不拆成列表。自然的问句、编号小标题和列表前的引导句是正常写法，保持原样。缺论证材料时，在终稿之后列出需要作者补充的内容，修改者不替作者编理由。

## 仓库内容

- `SKILL.md` 是 skill 主文件，包含写前、写时、改时的规则。
- `docs/ai-flavor.md` 讲 AI 味的发展与成因，附研究依据和引自 [lieflat-less-ai-tone](https://github.com/larashero3-dotcom/lieflat-less-ai-tone) 的语料统计；`SKILL.md` 的成因一节是它的摘要。
- `references/revision.md` 是修订稿的格式和规则，用户要求修订稿时读取。
- `docs/cases.md` 是修改案例，改规则之后用它做回归检查。
- `.github/ISSUE_TEMPLATE/bad-case.md` 是反馈改坏或改得不够的案例时用的模板。
- `CHANGELOG.md` 记录每个版本，以及各版借鉴和没有采纳的内容。
- `THIRD_PARTY_NOTICES.md` 列出参考项目的许可、版权声明和使用方式。

## 边界

事实、数字、日期、引文、来源、经历和结论以原文为准。否定、条件、范围、时间、完成状态和归因保持不变，“可能”与“确定”、“计划”与“已经”的区别保持原样；否定词约束的对象和范围一并保留，“不是因为权限不足”不能改成“权限充足”。判断的方向和强度不变，“系统性重塑”不降为“调整”。终稿里的每个实词都要能在原文或作者补充的材料里找到出处，找不到的删掉。学术作业和署名文本由作者本人完成。

## 已知局限

`docs/cases.md` 目前有十八个回归案例，每次改规则之后由维护者手动重跑，没有自动评测，也没有在不同模型之间做系统比较，规则在其他模型上的表现可能不同。

默认方式在词句上改得保守：比喻义的说法在所指无法确定时保留原词，作者的评价默认保留，包装词多的长文可能改得偏少。结构不受这个限制，默认就可以调整；要连词也一起清理，可以要求修订稿，或者明确要求写平实。修订稿收录的改动更多，出错的机会也更多，标“等义”的条目同样可能改变条件或范围，定稿之前请逐条看，尤其是标“推测”的条目。

结构调整之后，终稿可能比原文长，也可能短。原文的材料都会被保留或明确标出，但你熟悉的那几个小节可能换了位置，发布稿的文内锚点和其他文档里的链接可能因此对不上；遇到这种情况，可以在要求里写明保留结构。

段落推进和立场代价的判断依赖模型对论证的理解。作者没有提供材料时，这两步只能指出问题，无法替作者解决；终稿之后列出的待补充内容，需要作者本人完成。

## 反馈

改坏了或者改得不够，请用 [Bad case 模板](.github/ISSUE_TEMPLATE/bad-case.md)提交原文、你的要求和实际输出，并给出一个应当修改和一个应当保留的例子。请不要提交未经授权的聊天记录、密钥或个人信息。
