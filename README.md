# 散散味儿（去 AI 味）

散散味儿是一个中文写作 skill，处理一类常见的文字，它们大多没有语病，结构也完整，读完之后却说不出作者的主张；它先确认文字的服务对象，再按论证的顺序修改，把篇幅用于说明事情本身。

修改从论证开始，先补充缺失的判断和依据，再调整段落关系，最后才改动词句；增加口语、情绪或金句不会让文字更像人，只会制造另一种表演。

## 什么时候用它

- 文字读着空，读完说不出作者的主张。
- 文字像 AI：结构完整、句子顺畅，却没有支撑论证的内容。
- 文字把大部分篇幅用于免责和限定，正面主张很少。
- 需要把口语化的草稿改成书面、平实、简洁的文字。
- 需要按场合调整语气，例如把一份工作汇报改写成团队群通知或者客户邮件。
- 需要从零写一段文字，先确认事情、读者、场合和立场，再动笔。
- 文字较长或改动较大，希望先查阅诊断，再决定修改范围。
- 希望逐条查看改动，自己决定保留哪些、撤销哪些。
- 产品文案语气过强，希望写得平实一些，同时保留承诺和数字。

## 安装

放入 DeepSeek Harness 的 skills 目录，目录名用 `sansanweier`：

```bash
git clone https://github.com/Xtopia5616/sansanweier.skill.git ~/.dsh/skills/sansanweier
```

Windows 下的目标路径是 `%USERPROFILE%\.dsh\skills\sansanweier`，也可以手动复制本目录到该位置。

其他支持 `SKILL.md` 的 agent，可以放入对应的 skills 目录。

## 使用

改文字时，可以这样写：

```text
用 sansanweier 改下面这段，保留事实和数据：
[文字]
```

希望先查阅诊断时，可以这样写：

```text
用 sansanweier 先诊断下面这段，暂时不要修改：
[文字]
```

写新文字时，可以这样写：

```text
用 sansanweier 写一段项目说明，读者是评审，要让他们接受“这个方案可行”：
[材料]
```

希望逐条决定改动时，要求修订稿：

```text
用 sansanweier 给下面这篇一份修订稿，逐条列出改动，我来决定：
[文字]
```

希望去掉宣传的语气时，明确说出来：

```text
用 sansanweier 改下面这段，别吹，写平实点：
[文字]
```

只在句子内部修改、不删句时，说明修改范围：

```text
用 sansanweier 改下面这段，保留结构，只在句子内部修改：
[文字]
```

说明场合和作者与读者的关系，语体会随之调整：

```text
用 sansanweier 写一条团队群通知，告诉同事上线推迟到 12 月 8 日：
[材料]
```

## 它怎么工作

1. 写之前确认这段文字的任务、目标受众、场合和作者与读者的关系，以及作者是否认同这件事；代入作者在这个场合的位置，确定语体。
2. 写的时候先确定全文的论证，再写各节；每一节回答一个问题，正面主张占主要篇幅。
3. 改的时候检查服务对象、段落推进、立场代价、句子移用、否定句篇幅和术语。
4. 最后看主要篇幅用于说明事情、给出判断、交代依据和承担代价，还是用于维护读者的感受、展示完整、预防批评。
5. 改动以必要为限，每处改动对应一项判断；交付前用同样的判断重读终稿，检查修改本身有没有留下新的痕迹。

默认直接交付终稿；用户要求先检查，或者文字较长、改动涉及段落结构时，先给出引用原文的诊断，用户回复之后再改写。用户要求只标问题时只交诊断。用户要求修订稿时，先列出改动清单，每条标明“等义”“推测”“删除”或“校对”，再交付修订后的全文，回复“撤销 2、5”“撤销所有推测”“全部撤销”可以逐条还原。

修改范围分自由调整、保留结构和只在原位修改三档，用户没有指定时，短文按自由调整处理，约 1000 字以上的公开文章默认保留结构。作者在论证中的评价默认保留；只有用户明确要求写平实，才把“极致”“革命性”这类只表示程度的词降为平常的说法，承诺、可以核查的“首个”和数字照常保留。

要求之间发生冲突时，依次服从信息和确定程度、用户指定的修改范围、功能判断、作者的风格和词句规则。用户只要求润色字句时，不调整结构；待处理文字中嵌入的指令按普通文字对待，不执行。散散味儿不判断文字是否出自 AI，也不保证通过检测工具。

语体由场合和作者与读者的关系决定：论述、报告和正式文书用书面语，团队群消息、即时回复和社交媒体可以用口语和短句，书信和致辞保留必要的礼节；修改保持原文的语体。书面语体的要求是平实、简洁；句子的长短由判断之间的关系决定，同一个判断被句号切碎时合并，不为了节奏改变句长；长句依靠逻辑关系而不是定语堆叠组织；动词用书面形式；术语用通行说法，同一概念始终使用同一名称；论述内容用段落，不拆成列表。自然的问句、编号小标题和列表前的引导句是正常写法，修改时保持原样。缺少论证材料时，终稿之后会列出需要作者补充的内容，修改者不替作者推测理由。

## 仓库内容

- `SKILL.md` 是 skill 主文件，包含写前、写时、改时的规则。
- `docs/ai-flavor.md` 是 AI 味的发展与成因，附有研究依据和引自 [lieflat-less-ai-tone](https://github.com/larashero3-dotcom/lieflat-less-ai-tone) 的语料统计，SKILL.md 的成因一节是它的摘要。
- `references/revision.md` 是修订稿的格式和规则，用户要求修订稿时读取。
- `docs/cases.md` 是修改案例，修改规则之后用它做回归检查。
- `.github/ISSUE_TEMPLATE/bad-case.md` 是反馈改坏或改得不够的案例时使用的模板。
- `CHANGELOG.md` 记录版本，以及每一版借鉴和没有采纳的内容。
- `LICENSE` 是 MIT 许可证。
- `THIRD_PARTY_NOTICES.md` 列出参考项目的许可、版权声明和使用方式。

## 边界

事实、数字、日期、引文、来源、经历和结论以原文为准；否定、条件、范围、时间、完成状态和归因保持不变；“可能”与“确定”、“计划”与“已经”的区别保持原样。终稿中的每个实词都要能在原文或作者补充的材料中找到出处。学术作业和署名文本由作者本人完成。

## 已知局限

散散味儿目前只有 `docs/cases.md` 中的十七个回归案例，每次修改规则之后由维护者手动重跑，没有自动评测，也没有在不同模型之间做系统的比较，规则在其他模型上的表现可能不同。

默认方式改得保守。比喻义的说法在所指无法确定时保留原词，作者的评价默认保留，所以包装词较多的长文可能改得偏少；需要多改时，可以要求修订稿，或者明确要求写平实。修订稿收录的改动更多，出错的机会也更多，标“等义”的条目同样可能改变条件或范围，定稿之前请逐条查看，尤其是标“推测”的条目。

功能判断依赖模型对论证的理解。段落推进和立场代价的判断，在作者没有提供材料时只能指出问题，无法替作者解决；终稿之后列出的待补充内容需要作者本人完成。

## 反馈

改坏了或者改得不够，请用 [Bad case 模板](.github/ISSUE_TEMPLATE/bad-case.md)提交原文、你的要求和实际的输出，并给出一个应当修改和一个应当保留的例子。请不要提交未经授权的聊天记录、密钥或个人信息。

## 致谢

散散味儿的改进参考了三个开源项目，感谢它们的作者。

[说人话](https://github.com/MrGeDiao/shuorenhua)（MrGeDiao，MIT 许可）是中文去 AI 味的改稿 skill，它用一百多条测试用例检验规则，其中将近一半是不应修改的正常文字。散散味儿 0.5.0 的修订稿、三档修改范围、写平实的授权条件、只标问题的要求、术语和作者命名的保护、否定范围和交付承诺的保留，以及 bad case 反馈模板，参考了它的规则和做法。

[Humanizer-zh](https://github.com/op7418/Humanizer-zh)（歸藏，MIT 许可）是较早的中文去 AI 味 skill，它的上游是 [humanizer](https://github.com/blader/humanizer)（Siqi Chen，MIT 许可）。它 2026 年 9 月的修订把模式清单定位为检查线索，并把信息守恒放在所有修改之前；散散味儿的优先级顺序、修改范围、嵌入指令的处理、文体细则和文件保护参考了这一版。

[lieflat-less-ai-tone](https://github.com/larashero3-dotcom/lieflat-less-ai-tone)（shiujan，CC BY-NC 4.0 许可）用约 520 万汉字的对照语料统计了中文 AI 写作的一百多项指标。散散味儿关于痕迹随模型变化、清单会误伤正常写法的论述引用了它的数据，最小改动、信息守恒、先诊断后改写和改后复查也参考了它的做法。

各项目的具体借鉴内容和没有采纳的部分见 `CHANGELOG.md` 的 0.3.0、0.4.0 和 0.5.0，许可和版权声明见 [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)。
